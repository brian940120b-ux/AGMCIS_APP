## 1. Position Sizing:倉位不再是固定數字

原本的系統是「倉位固定 1000 USDT,槓桿由信心分數決定」。

這是反過來的。倉位固定代表**每一筆承擔的風險完全取決於停損放多遠** ——
停損放 1% 的那筆虧 10 USDT,停損放 10% 的那筆虧 100 USDT,
但兩筆都被當成「一個單位的風險」。

正確的順序:

```
1. 先決定這一筆最多可以虧多少   = 權益 × 風險%
2. 由停損距離反推名目價值       = 風險金額 ÷ 停損距離%
3. 由槓桿決定要押多少保證金     = 名目 ÷ 槓桿
```

### 核心觀念:名目價值與槓桿無關

權益 10000、風險 1%、停損距離 3% 時:

| 槓桿 | 名目 | 保證金 | 風險 |
|---|---|---|---|
| 1x | 3333.33 | 3333.33 | **100.00** |
| 3x | 3333.33 | 1111.11 | **100.00** |
| 5x | 3333.33 | 666.67 | **100.00** |
| 10x | 3333.33 | 333.33 | **100.00** |

調高槓桿**不會讓你冒更多風險**,只會讓同樣的部位佔用比較少的保證金。
但它會讓強平價變近,所以槓桿另有一條獨立的限制(見下一節)。

有測試鎖住這個性質:五種槓桿算出來的風險金額必須完全相同。

### 停損越遠,倉位越小

| 停損距離 | 名目 | 風險 |
|---|---|---|
| 1% | 10000.00 | 100.00 |
| 3% | 3333.33 | 100.00 |
| 10% | 1000.00 | 100.00 |

這就是固定倉位做不到的事。

### 不硬補到最小名目

名目低於交易所最小值時**直接拒絕開倉**,不把它補到最小值。
補上去會讓這一筆的風險超過設定上限 —— 那等於偷偷破壞風控。

### 被縮小時回報實際風險

曝險上限或可用餘額會把名目縮小。縮小之後實際風險也跟著變小,
`SizingResult` 回報的是**實際值**而不是原本打算承擔的值。

## 2. 槓桿:由風險驅動,不是信心

原本是 `confidence >= 95 -> 8x`。這很危險:
信心是對**方向**的判斷,槓桿是對**能承受多少逆向波動**的設定,兩者沒有因果關係。
訊號很強但市場波動很大的時候,高槓桿只會讓你在正確的方向上被洗出場。

`decide()` 的函式簽名**刻意沒有 confidence 參數**,並有測試鎖住這件事。

### 最重要的一條:強平價必須比停損遠

槓桿 N 倍時,價格逆向走約 1/N 就接近強平。
如果停損距離比 1/N 還遠,**停損還沒觸發就先被強平了** ——
等於停損形同虛設,而且虧掉的是全部保證金,不是預設的風險金額。

```
槓桿上限 = 安全係數 × 100 / 停損距離%
```

安全係數取 0.5(理論值的一半),留給維持保證金與手續費。

| 停損距離 | 槓桿上限 | 強平大約在 |
|---|---|---|
| 1% | 50.00x | 2.0% |
| 3% | 16.66x | 6.0% |
| 10% | 5.00x | 20.0% |
| 25% | 2.00x | 50.0% |

其他限制:ATR 佔價格比例(≥5% → 1x、≥3% → 2x、≥1.5% → 3x)、
多時間框架未同向 → 2x、合約本身上限、風控全域上限。

### 一個被測試抓到的錯誤

我原本用 `round(candidate, 2)`。`round(16.666…, 2)` 得到 **16.67**,
那比真正的上限 16.666 還高 —— 進位偷偷放寬了安全限制。

改成無條件捨去。與 Phase 4 數量進位的原則一致:
**調整只能讓事情更保守,不能更寬鬆。**

有一個不變量測試跑遍 13 種停損距離 × 6 種上限,
確認 `decide()` 產生的槓桿一定通過 `stop_is_safer_than_liquidation()`。
同時也把兩個函式的邊界對齊 —— 原本 `decide()` 允許等於上限,
但安全檢查用嚴格小於,在邊界上會出現「批准的槓桿卻被判定不安全」的矛盾。

## 3. Risk Engine:唯一的裁決入口

`RiskEngine.evaluate(intent, state)` 回答三個問題,順序不能顛倒:

1. **現在可不可以開新倉?**(帳戶層級閘門)
2. **這一筆該用幾倍槓桿?**(停損距離 + 波動度)
3. **這一筆該押多少保證金?**(風險 ÷ 停損距離)

閘門檢查:緊急停止旗標、交易暫停旗標、自動交易開關、最大回撤、
總曝險、持倉數、總浮虧、單日虧損、連續虧損、單日交易次數。
Profit Factor 偏低只**警告**不阻擋。

最後還有一道:即使倉位算得出來,若槓桿會讓強平價比停損近,一樣拒絕。

### 純函式設計

`AccountState` 是一個資料結構,由呼叫端提供。引擎**不自己去查資料庫** ——
自己查會讓每次判斷都打一次資料庫與 API,而且沒辦法寫測試。
`agmcis/risk/account_state.py` 負責從現有資料層組出這個快照。

## 4. Kill Switch:不只是停止新開倉

原本的「緊急停止」只做一件事:停止新開倉。
但真正需要 kill switch 的時候,已經掛在市場上的單與已經持有的部位還在承擔風險。

刻意分成兩段:

| 動作 | 做什麼 | 誰用 |
|---|---|---|
| `arm()` | 停新單 + 關自動交易 | **自動風控**(安全、可逆、不動部位) |
| `panic()` | 停新單 + **撤所有掛單** + **平所有部位** | **人工**(需要明確意圖) |

分開是刻意的:自動風控觸發時不該擅自平掉使用者的部位,
那是很大的動作,應該由人決定。有測試鎖住 `arm()` 不會碰到平倉。

### 三個細節

- **`panic()` 先停新單再撤單平倉** —— 撤單與平倉期間絕對不能又開新倉。有測試驗證順序。
- **部分失敗不中止其他步驟** —— 能撤的先撤、能平的先平,失敗的記在 `errors`。
  緊急狀況下「做到多少算多少」比「一個失敗全放棄」好。
- **沒接上撤單/平倉能力時明確回報** —— 不會靜默跳過讓人以為已經平掉了。

### 稽核

每一個動作都寫 JSON Lines 稽核紀錄,包含觸發者、時間、原因、結果。
**`disarm()` 也會記錄** —— 誰在什麼時候把保險打開同樣重要。
稽核寫入失敗不會中止緊急操作,但會用 exception 級別記錄。

## 5. 接進實際交易路徑

`auto_trader.py` 重寫成完整鏈路:

```
scan_market()
  -> TradeIntent        建構時強制驗證停損存在且方向正確
  -> Risk Engine        要不要開?幾倍?押多少?
  -> create_paper_trade
```

順序上有一個重要的安排:**帳戶層級的閘門在掃描之前跑**。
閘門只查資料庫很便宜,掃描要打交易所 API。被擋下時沒必要浪費那些請求。
(我第一版把閘門放在掃描之後,是被原有的測試抓出來的。)

迴圈內的區分也很重要:
- **單一標的被拒**(名目太小、重複倉位、強平風險)→ 試下一檔
- **帳戶層級被封鎖**(回撤、單日虧損)→ 立刻結束,對所有標的都一樣
