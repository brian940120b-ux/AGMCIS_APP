## 3. 人工確認檔

```bash
python scripts/live_gate.py       # 它會印出範本
```

檔案:`live_gate_confirmation.json`

```json
{
  "phrase": "我已經讀過 docs/PHASE_17_REPORT.md,我了解這個系統可能會虧光我投入的所有資金,我確認要用真實資金交易",
  "signed_at": "2026-09-11T12:00:00+00:00",
  "approved_notional_usdt": 20
}
```

三個限制,每一個都有理由:

- **確認句要逐字相符。** 它很長是刻意的:短句子容易被複製貼上,
  長句子會逼人讀過一次。
- **24 小時後過期。** 「上個月批准過」不等於「現在批准」。
- **必須指名單筆名目上限,而且不得超過 50 USDT。**
  「批准過一次」不等於「批准所有金額」。第一次用真錢跑的規模,
  應該小到虧光也不影響任何事。

這個檔案**不進版控**。它是「這個人在這個時間點批准了這個金額」的憑證,
提交進 git 等於把那個決定變成永久的、對所有人生效的。

## 4. 失敗是預設結果

每一項檢查在**自己壞掉時回傳「沒通過」**,不是「跳過」。

> 一個在自己壞掉時預設放行的安全閘門不是安全閘門。

這一點我第一版寫錯過。`check_reconciliation` 原本是這樣:

```python
if summary.get("naked_count"):
    problems.append(...)
```

資料庫連不上時 `_summary()` 回傳的每個計數都是 `None`,
於是這一項**通過了**。在真實情境裡那代表:資料庫掛掉的時候,
閘門會認為「沒有裸倉」。

修正後它會檢查必要欄位是否存在,缺了就明說「讀不到資料不等於沒問題」,
並且把任何一則 critical 警示都當成不通過。

稽核也採同一個原則:**每一次評估都記錄,包含沒通過的那些**。
只記錄通過的評估會讓稽核紀錄變成一份成功史 ——
事後要回答「當時為什麼會放行」,需要看到它前面失敗了幾次。

## 5. 閘門開啟 ≠ 會下實單

**即使九項全部通過,系統仍然無法送出真實訂單** —— `LiveBroker` 不存在。

這不是疏漏,是設計。閘門是實單的**前提**,不是開關。
第 8 項檢查的通過條件就是「它不存在」,而且那一項是 non-blocking 的提醒,
並且如果哪天 `broker` 模組真的出現 live 命名的東西,它會**變成 blocking 並關閉閘門**。

真的要接實單時,那段程式碼本身必須再經過一次獨立的審視 ——
不是「閘門開了所以可以寫」。

測試的方向跟其他模組相反:重點不是「條件滿足時會不會開」,

- `test_a_provider_that_raises_counts_as_failed`
- `test_a_missing_provider_counts_as_failed`
- `test_an_expired_confirmation_is_rejected`
- `test_an_oversized_amount_is_rejected`
- `test_a_live_broker_appearing_would_close_the_gate`

同時保留一條「閘門也要能開」:`test_all_conditions_met_opens_the_gate` ——
一個永遠關著的閘門等於沒有做完。

## 7. 實話

把整個系統的狀態說清楚:

- **這套系統從來沒有用真錢跑過。** 模擬盤的成本模型接近真實,
  但模擬盤沒有滑價的不確定性、沒有部分成交、沒有交易所故障。
- **還沒有任何策略通過 Phase 8 的完整驗證。** 目前的資料量根本不夠。
- **合約規格還沒校準**(需要在 VPS 上執行,見 Phase 11 報告)。
- **回測與模擬的所有數字都來自合成或短期資料**,不是優勢的證據。
- Master Prompt 第二節的研究目標是 70-80% 勝率,但那**不是保證**。
  真實結果落在 55-65% 且 PF > 1.5、期望值為正,就是誠實且可接受的結果。

換句話說:**第 3、4、5 項條件目前都不會通過,而那是正確的狀態。**
