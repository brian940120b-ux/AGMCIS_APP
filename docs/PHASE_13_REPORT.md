## 1. 為什麼

Phase 12 的 `Order` 只活在記憶體裡。程式重啟時 `UNKNOWN` 狀態的訂單就消失了 ——
而那正是**最需要被記住**的狀態:系統不知道交易所收到了什麼。

忘記它等於放棄對帳;放棄對帳之後,任何重試都可能開出重複倉位。
所以 Phase 12 刻意沒有重試 —— 重試必須建立在對帳之上。

## 2. 訂單持久化

```
orders          每張單的當前狀態(client_order_id 唯一)
order_events    每一次狀態轉移的稽核軌跡
```

為什麼要事件表:出事之後要回答「那張單當時到底走到哪一步」,
只有最終狀態是不夠的。一張最後變成 `CLOSED` 的單,
是「正常成交後平倉」還是「裸倉被緊急平掉」,差別很大。

Execution Engine 的每一次狀態轉移都經過 `_move()`,先轉移再落地。
**寫不進資料庫時不會把狀態改掉是做不到的**(轉移在前),
所以改成:寫入失敗用 `logger.critical` 大聲說,並明確講出
「資料庫狀態已落後於真實狀態,對帳時會需要處理」——
已經送出去的單不能因為記錄失敗就消失。

## 3. 三個對帳問題

### 3.1 狀態不明的訂單成交了沒?

`UNKNOWN` / `TIMEOUT` / `SUBMITTING` 的單**不可以重送,只能查**。

| 查詢結果 | 處理 |
|---|---|
| 交易所查無此單 | `REJECTED` —— 可以確定它從來沒被接受 |
| 交易所說 filled / protected / … | 以交易所的狀態為準 |
| **查詢失敗** | 維持不明,回報差異。**不可以當成「查無此單」** |
| 回傳的狀態無法辨識 | 維持不明,回報差異,不猜 |
| 與本地狀態邏輯矛盾 | 回報差異,**不硬寫** |

第三條是刻意分開的:`fetch_order()` 回傳 `None` 代表「可以確定沒有這張單」,
查詢失敗要**拋例外**。把查詢失敗當成 `None`,會讓一張其實已經成交的單
被標成 `REJECTED` —— 然後系統會以為自己沒有倉位。

最後一條也一樣重要:本地說 `CLOSED`、交易所說 `FILLED`,兩邊在邏輯上兜不起來。
硬寫進去只會把矛盾藏起來,所以狀態機不允許的轉移一律回報成差異。

### 3.2 本地有的部位,交易所真的有嗎?

不一致時**交易所永遠是事實來源**。本地紀錄是系統對現實的看法,不是現實本身。

數量差異用 1% 容忍度 —— 浮點與交易所的精度處理會有微小差距,那不是差異。

### 3.3 交易所有、本地不知道的部位

最危險的一種:**一個沒有人在管的倉位。** 沒有停損、不會被監控、
也不在風控的計算裡。這種差異標記為 critical。

另外不需要交易所也能查的一項:本地部位沒有停損 → `UNPROTECTED_POSITION`。

## 4. 鐵律:對帳只更正紀錄,絕不下單

想「順手把多出來的倉位平掉」是很自然的念頭。但對帳跑在排程裡、
**在資料不完整時也會跑** ——

> 一個會自動平倉的對帳程式,在交易所 API 回傳空清單的那一刻
> 會把整個帳戶清空。

所以它只回報。平倉留給人,或留給明確的流程(裸倉巡檢是另一條路徑,
它的判斷依據是本地資料,不依賴交易所回應)。

有測試掃描 `reconciliation.py` 的原始碼,確認它連 import 都碰不到
任何能下單的東西。

---

## 5. 模擬盤的限制,寫成測試而不是藏著

模擬盤沒有訂單簿,只有交易列。所以:

- `fetch_order()` 用「這個標的現在有沒有倉位」來回答「這張單怎麼了」。
  有停損回 `protected`、沒停損回 `filled` —— 這個差別是有意義的,
  `filled` 但沒 `protected` 就是裸倉。
- `fetch_positions()` 回傳的就是交易表本身。也就是說
  **模擬盤的部位對帳是拿同一份資料跟自己比,永遠不會發現差異。**

第二點不是缺陷,是模擬盤的本質。真正的部位漂移只有實盤才驗得出來。
`test_paper_position_reconciliation_compares_data_with_itself` 把這件事
寫成測試,免得以後有人以為模擬盤跑過對帳就等於驗證過了。

## 7. 尚未做的事

- **重試仍然沒有加。** 現在對帳有了,重試在技術上變得可行,
  但要先定義清楚「什麼情況下重試是安全的」。這一步寧可晚一點。
- **`fetch_order` 在實盤要真的查交易所訂單**,不能沿用模擬盤那套
  「看有沒有倉位」的近似。
- **部分成交仍未走過真實路徑。**
- **沒有自動修復。** 所有差異都只回報。這是刻意的,但長期需要一個
  明確的、人核可的修復流程(例如「確認要把這個孤兒倉位納管」)。
- **order_events 沒有保留期限。** 高頻運行下這張表會長很快。
