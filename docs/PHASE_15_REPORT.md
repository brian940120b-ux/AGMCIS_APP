## 1. 設計目標

這一層回答的問題跟 Dashboard 不一樣。Dashboard 說「現在怎麼樣」,
這裡說:**哪些東西其實沒有貢獻?**

那是個不舒服的問題,所以很容易被做成一份只講好消息的報告。
而一份只會說好消息的檢討報告**比沒有檢討報告更糟** ——
它會讓人對一個沒有優勢的系統產生信心。

所以整個模組是圍繞著「能不能說出壞消息」設計的:

- 樣本不足時**不給結論**,明說「還不知道」。
- 拿不出正貢獻的 Agent 會被明確列出來,不是留在平均值裡稀釋掉。
- 沒有歸因資料的舊交易一律**排除**,不補預設值。

---

## 2. 歸因資料必須在開倉當下記下來

Migration 005 幫 `trades` 加了 `agent_votes`、`market_regime`、
`strategy`、`confidence`。

**事後推不回來。** Agent 的投票取決於當下的指標,而指標會隨時間變。
沒有在開倉當下記下來,那筆交易的歸因就永遠遺失了。

資料從 `TradeIntent` 一路傳到資料庫:

```
Consensus -> TradeIntent.agent_votes
  -> PaperBroker.submit_entry -> create_paper_trade -> insert_trade
```

舊交易沒有這些欄位,一律留 `NULL` 並在分析時排除。
補一個預設值會讓歸因統計看起來有樣本,而那些樣本是憑空造的。

---

## 3. 歸因:總體數字沒有用

一個總體的「勝率 58%」沒有用。有用的是:

> 「這 58% 全部來自盤整市,趨勢市裡是 41%。」
> 「扣掉最好的三筆,期望值是負的。」

`attribution.py` 把損益拆到五個維度:市況、策略、出場原因、標的、方向。
每個分群都帶 `reliable` 標記,低於 20 筆的分群不下結論。

**集中度檢查**是第二句話的來源:扣掉最好的三筆之後期望值變負,
代表這套系統其實沒有優勢,只是運氣好抓到幾根大的。那幾根通常不會重演。

兩個刻意的設計:

- 分類鍵是 `None` 的交易**排除**,不歸進一個叫「未知」的桶子。
  那個桶子的統計沒有意義,而且會讓人以為那是一個真實的分類。
- 沒有虧損單的分群 Profit Factor 回 `None` 而不是無限大。
  無限大會讓排序把一個只有兩筆交易的分群排到第一。

## 4. Agent 貢獻度需要統計檢定,不是比大小

十二個 Agent 裡一定有幾個是沒用的。問題是哪幾個。

對每個 Agent 問三件事:

1. **它有沒有在發言?** 棄權率 90% 以上 → `SILENT`。
2. **它同意時結果比較好嗎?**
3. **那個差別是真的還是運氣?**

第三點是這個模組最重要的部分,而且我第一版寫錯了。

原本的判定是「同意時的期望值 > 反對時的期望值 → CONTRIBUTING」。
我用一個**完全隨機投票**的假 Agent 去測,它被判成 `CONTRIBUTING`。
那是必然的:隨機投票有一半的機會讓同意組的平均比較高。

改成算兩組平均差距的標準誤,差距小於 **2 個標準誤**時一律判 `UNKNOWN`。
修正後同一份資料:

| Agent | 判定 | 差距 |
|---|---|---|
| trend(真的有資訊) | CONTRIBUTING | 19.96 σ |
| momentum(隨機投票) | UNKNOWN | 0.62 σ |
| news(永遠棄權) | SILENT | n/a |

這是個粗略的檢定,不是嚴謹的統計推論,但它足以擋掉這一類假陽性。

判定有四種,`UNKNOWN` 是完全合法的結論:

```
CONTRIBUTING  同意時明顯比反對時好
NO_EDGE       同意時明顯比反對時**差** —— 票的方向可能是反的
UNKNOWN       跟雜訊分不出來,或樣本不夠
SILENT        幾乎不發言
```

## 5. 刻意不做的事:自動關掉沒貢獻的 Agent

樣本小的時候,「沒貢獻」跟「運氣不好」分不出來。
自動關掉會讓系統在每一次小樣本的波動裡改變自己的組成 ——
**那是過擬合的另一種形式。**

所以這一層只回報。報告裡明確寫著「這不是自動關掉它們的理由,調整由人決定」,
而且有測試掃描原始碼確認 `agent_scorecard.py` 碰不到 registry。

## 6. 自我檢討報告

四種判定:

| 判定 | 意思 |
|---|---|
| `HEALTHY` | 有正期望值,樣本夠,而且不依賴少數幾筆 |
| `FRAGILE` | 有正期望值,但扣掉最好的三筆就變負 |
| `LOSING` | 期望值為負 |
| `NOT_ENOUGH_DATA` | 樣本不夠,**不下結論** |

報告有兩個區塊:**發現**與**目前答不出來的問題**。

第二個區塊跟第一個一樣重要。看報告的人需要知道哪些結論還沒有依據,
否則他會把沉默當成「沒問題」。

`LOSING` 與 `FRAGILE` 會浮到透明度面板頂端的警示列;
`NOT_ENOUGH_DATA` **不會** —— 樣本不夠是常態不是異常,
把它做成警示會讓真正的警示被淹沒。

## 8. 後續補上的兩件事

### 8.1 多重比較校正

原本的 2 個標準誤門檻是**單獨看一個 Agent** 時的標準。
但我們同時看十二個:各有約 5% 的機率純屬巧合,
至少一個假陽性的機率是 1 - 0.95¹² ≈ **46%**。

也就是說:一套全部由隨機投票組成的 Agent 群,有將近一半的機會
會產生「至少一個有貢獻的 Agent」。那個結論毫無意義,
但它看起來跟真的一模一樣。

現在門檻依同時比較的數量做 Bonferroni 校正
(12 個 → 2.87 個標準誤),並在報告裡說明為什麼拉高。
校正是保守的,所以另外有一條測試確認**真的訊號仍然認得出來**。

### 8.2 時間維度

`attribution.trend()` 按月分群,比較「最近一個月」與「更早的月份」。
最近掉到先前的一半以下就標記為衰退,而且自我檢討的判定會從
`HEALTHY` 降為 `FRAGILE` —— 整體期望值還是正的,但那跟「穩定獲利」
是兩件事。

刻意不做線性迴歸:交易月數通常是個位數,在那麼少的點上擬合一條線,
斜率幾乎完全由雜訊決定。

「先前就在虧」的系統不會被稱為「衰退」—— 那不是正確的描述。

## 9. 仍然沒做的事

- **Agent 貢獻度只看方向票。** 觀望票的價值(擋下了多少虧損)
  完全沒有衡量 —— 那需要記錄「被擋下來的交易後來會怎樣」,
  而那本身就是反事實,不容易做得誠實。
- **歸因只涵蓋模擬盤。** 實盤的歸因要等實單路徑走通。
- **Bonferroni 是最保守的校正。** 它會讓真的有貢獻的 Agent 比較難被認出來。
  在這個場景保守是對的,但它不是唯一的選擇。
