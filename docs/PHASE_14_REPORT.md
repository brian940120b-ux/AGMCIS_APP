## 1. 問題

Phase 9 到 13 加了很多東西:Agent 投票、訂單狀態機、裸倉自動平倉、
對帳差異、成本統計、規格校準狀態。

到目前為止這些**只在 log 裡**。

看不到就等於不存在。而更糟的是:你分不出「沒有問題」與
「壞掉了所以什麼都沒回報」。一個會在背景默默把裸倉平掉、
默默發現對帳差異的系統,如果沒人看得到它做了什麼,
那些機制的價值會被打掉一大半。

## 2. `/transparency`

五個區塊,各自獨立載入:

| 區塊 | 回答的問題 |
|---|---|
| Agent 投票 | **系統為什麼沒有交易?** |
| 訂單狀態 | 有沒有狀態不明的單?有沒有裸倉? |
| 對帳 | 本地與交易所有沒有差異? |
| 成本 | 扣掉手續費與資金費用之後還剩多少? |
| 規格校準 | 哪些數字是真的,哪些是猜的? |

第一個是最常用的。大多數時候「為什麼沒有交易」的答案是某個環境型 Agent
投了觀望,而那在 log 裡要翻很久。現在每個標的的十二張票直接列出來。

頁面上也寫著棄權與觀望的差別 —— 那個區別在 Phase 6 與 Phase 9 各付過一次代價,
不該只活在程式碼註解裡。

## 3. 頂端狀態列只講需要注意的事

```
沒有需要注意的事項。(這本身就是有意義的資訊 —— 不是「還沒檢查」。)
```

有事的時候才列:

| 情況 | 等級 |
|---|---|
| 已成交但沒有停損保護 | critical |
| 對帳發現需要立刻處理的差異 | critical |
| **某一區塊讀取失敗** | critical |
| 有狀態不明的訂單 | warning |
| 合約規格尚未校準 | warning |

第三條是刻意的。某一塊讀不到資料時如果只是安靜地少一塊,
看的人會以為那裡沒有問題 —— 那正是這個面板要消滅的狀況。
所以區塊失敗會變成一則 critical 警示,而不是空白。

## 4. 全部唯讀

這一頁沒有任何一個端點會下單、平倉或改設定。兩個測試守著:

- 掃描 `api/transparency.py` 的原始碼,確認碰不到任何下單函式。
- 確認每一條路由都只有 `GET` —— GET 依定義不該變更狀態。

對帳端點會**跑一次對帳**,那看起來像是有副作用,但對帳本身就只更正
本地紀錄、回報差異,絕不下單(Phase 13 的鐵律),所以從 API 觸發是安全的。

## 5. 順手補上的一個漏洞

原本只有 `/api/` 的端點有「每個都要金鑰」的測試,**頁面本身沒有**。
新增頁面時很容易只記得保護 API,忘了頁面 —— 而頁面上的資料跟 API 是同一份。

現在 `test_every_html_page_requires_a_key` 會列舉所有非 API 路由並逐一檢查。
