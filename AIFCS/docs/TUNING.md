## 四、規則明文允許我們改的 ← **這裡就是可以贏的地方**

### 4.1 演算法：幾乎不限

> 可以使用 Rule-Base、行為樹、決策樹、貝葉斯、AI、機器學習、深度學習、
> 強化學習、LLM、等**非人工干預**之控制技術

**混合式是合法的。** 純 RL 不是規定。例如「RL 主控 + 規則式防墜底線」完全可行 ——
以我們目前的墜毀率來看，這可能比再多練幾百萬步有用。

### 4.2 整個連線程式：可以重寫

> 參賽方可根據本程式進行修改、或是**重新以其他程式語言撰寫**，
> 並無強制限制需要按照本範例進行開發

**所以下面每一個數字都是我們的**，不是 HOST 的：

| 參數 | 範例程式的值 | 規則上限 | 備註 |
|---|---|---|---|
| 死區 | `[0.01, 0.03, 0.06]` | 無 | 小輸入被吃掉 |
| 指數曲線 | `[1.0, 3.0, 3.0]` | 無 | 升降舵/方向舵被三次方大幅衰減 |
| 每幀變化上限 | `[0.050, 0.026, 0.013]` | 無 | **升降舵滿舵要 0.64 秒** |
| 油門變化率 | `0.004` / 幀 | 無 | 0→1 要 4.2 秒 |
| **方向舵上限** | **0.2** | **±1** | 差 5 倍 |
| 高速升降舵限制 | Mach 0.8 以上 0.4 | 無 | 自己加的 G 限制器 |

**最值得注意的是方向舵。** 三個數字在打架：

- **規則（表 2）：±1**
- 範例連線程式：clip 到 ±0.2
- 範例**訓練**環境的動作空間：釘死在 `[0, 1e-17]`

第三個代表**主辦方那顆 3.14 億步的模型從來沒動過方向舵**。用其他隊多半也是照抄
那個動作空間。**方向舵是規則允許、而對手很可能不會用的操作面。**

⚠️ 但每幀變化上限拿掉要小心：拉太猛會超過 9G，**每秒扣 1000 分**，而追蹤一秒
才賺 2000。整形不全是累贅，它也是個 G 限制器。**要 A/B，不要憑感覺改。**

### 4.3 訓練環境：完全是我們的

> A. 訓練階段軟體訓練程式：本程式為供參賽者快速上手之範例…**後續需要各參賽者
> 自行修改**

獎勵函數、對手、初始條件分布、課程學習、self-play —— 全部隨我們。

### 4.4 回合之間可以換模型

> 注意事項 3：參賽者可於單回合結束時且於新一回合開始前**切換模型或切換演算法**
> （回合切換 3 分鐘）

**這是一個戰術層面的機會。** 5 戰 3 勝的話，第一回合打完就知道對手的風格，
第二回合可以換一個針對性的模型。前提是我們手上要有**不只一個**訓練好的模型。

## 四之二、量到的結果(2026-09-26,v4)

同一批 20 個回合(seed 1000),對手 reference,配對比較:

| | won | killed | crashed | margin | 152-500m | floor |
|---|---|---|---|---|---|---|
| 什麼都不做 | 0% | 0% | **100%** | +18 | 0.2 | — |
| 什麼都不做 + 地板 | 65% | 0% | 0% | +51 | 0.2 | 6% |
| run1(5,000,000 步) | 0% | 0% | 95% | +63 | 0.3 | — |
| run1 + 修好的地板 | 55% | 0% | 0% | +1 | 0.3 | — |
| **v4(2,000,000 步)** | **100%** | **10%** | **0%** | **+11,169** | **40.3** | **1%** |

```bash
train.bat --name v4 --reward margin --ground-avoidance --g-limit 9 \
          --action-repeat 6 --gamma 0.995 --gradient-steps -1 \
          --observation extended --timesteps 2000000
```

7.4 小時,75 步/秒。`--action-repeat 6` 讓每個決策 = 6 幀,所以它看到的是
**1,200 萬幀** —— 比 run1 的 500 萬幀多 2.4 倍,雖然「步數」數字比較小。

**`killed` 第一次不是 0。** 在這之前 80 個回合、四種設定,一次 3 秒追蹤都沒有。

**`floor` 是 1%,比什麼都不做的 6% 還低。** 地板幾乎沒出手 —— 這個成績是策略
自己飛出來的,不是被規則層抱著飛完的。那一欄就是為了分辨這兩件事才加的。

### 哪一項貢獻最大,沒有拆開量

v4 一次動了五項:margin 獎勵、地板、G 限制器、action repeat 6、gamma 0.995、
extended 觀測。**沒有做消融實驗**,所以「哪一項最有效」目前無法回答,只知道
這一組合在一起有效。診斷鏈(1.7 秒視野太短、參考獎勵的接地懲罰在視野外、
沒有地板、Mach 限制砍半轉彎率)每一環都有獨立的量測支持,但那不等於證明了
每一環對這個結果的貢獻。

### 還沒證明的事

對手是 **reference —— 一架直線飛的靶機**。文件前面就寫著:一個什麼都不做的
策略對它都能贏 67%。**對靶機 100% 是必要條件,不是充分條件。**

真正的檢驗是 `--opponent pursuit`,而它把事情講得很清楚:

| 對手 pursuit | won | killed | margin | 152-500m | floor |
|---|---|---|---|---|---|
| **v4** | 100% | **0%** | +5,306 | **2.0** | 1% |
| **什麼都不做** | **90%** | 0% | +94 | 0.2 | 6% |

**甜蜜點停留從 40.3 秒崩到 2.0 秒,擊殺回到 0%。** v4 對會動的目標靠不近 ——
那 40 秒和那 10% 擊殺,是一架直線飛的靶機給的。

**而且搖桿置中對 pursuit 贏 90%,對靶機只贏 65%。** 我們的 `pursuit` 對手
**比靶機還弱**。所以「改用 pursuit 當課程」這條路是死的:那不是更難的對手。

### 結論:對手是瓶頸,不是策略

兩個內建對手都被搖桿置中打敗(65% / 90%)。**我們沒有任何一個會威脅到自己的
對手**,對著它們再練多久,學到的都是怎麼欺負不會反擊的東西。

下一步是 self-play:v4 是第一個值得放進對手池的快照。

## 四之二之二、`MemoryError`:對手池不能裝模型

v5 第一次跑 self-play,還沒開始第一個回合就死了:

```
File "...multiprocessing/spawn.py", line 132, in _main
  self = reduction.pickle.load(from_parent)
MemoryError
```

**不是記憶體不夠,是設計錯了。** Windows 沒有 `fork`,`SubprocVecEnv` 會把整個
環境設定**序列化給每一個 worker**。對手池裡放的如果是「已經載入的 SAC 模型」,
那就是 N 份神經網路同時擠在管線裡。

現在池子裡放的是 `LazyOpponent` —— **只帶路徑**,每個 worker 第一次用到時自己
從硬碟載。一個 process 一份,而不是「N 份同時穿過一根管子」。

**然後它用另一種方式死了第二次:**

```
OMP: Error #137: Cannot create thread.
OMP: System error #1450: 系統資源不足
```

每個 worker 自己載模型 = 每個 worker 各自 `import torch` = 每個各自開一整組
**OpenMP 執行緒池**,大小按 CPU 核心數算。八份。

在對手池出現之前,worker 裡只有 JSBSim 和 numpy,**完全沒有 torch**。

### 修法:worker 不需要 torch

SAC 的 actor 就是一個小 MLP —— 兩層隱藏層加一個線性輸出。前向傳播是**三次矩陣
乘法加一個 tanh**,numpy 就夠了。

現在權重在**父程序**(唯一本來就有 torch 的那個,因為它在訓練)抽成 numpy 陣列,
送給 worker 的就只是幾個陣列。worker 回到自我對戰出現之前的樣子。

**對照 SB3 自己的 `predict` 驗證過:** 200 個隨機觀測 × 3 種架構 × relu 和 tanh,
**最大差 1.8e-07** —— 那是 float32 對 float64 的捨入,不是近似。

> 只支援 SAC。PPO 的 actor 結構不同、squash 方式也不同,猜它不如講清楚不支援。

### 以及 worker 本來就不該開執行緒池

上面那個 numpy 修法沒有讓 OMP 錯誤消失,因為 **worker 一直都在 import torch** ——
不是為了對手池,是為了 `Monitor`。它在 builder 的 closure 裡被參照,所以 worker
一解 pickle 就會 import Stable-Baselines3,連帶 torch,連帶一整組按 CPU 核心數
開的 OpenMP 執行緒池。八份。

**worker 做的是純量的 JSBSim,加上一個小 numpy MLP 的前向傳播。它不需要執行緒池。**

`OMP_NUM_THREADS` 只在 OpenMP **初始化那一刻**被讀一次,而那一刻在 worker 裡
早於我們任何一行程式碼。所以現在是在**父程序 spawn 的那一瞬間**設成 1
(子程序繼承父程序的環境),spawn 完立刻還原 —— 父程序要跑梯度更新,它該用
整台機器。

**如果還是 1450 或 `MemoryError`**,那才是真的資源不夠,降 worker 數:

```bash
train.bat --name v5 ... --workers 4
```

## 四之三、整夜掛著跑(筆電)

**電腦關掉就沒有東西在算。** 訓練跑在你筆電的 GPU 上,沒有辦法繞過去。能做的是
讓它在你不在的時候安全地跑完。

### 程式已經幫你擋掉的

訓練一開始就會叫 Windows 不要進睡眠(`KeepAwake`),主控台會印:

```
sleep:    held off — but closing the lid still sleeps (see docs/TUNING.md)
```

沒印這一行,或印的是 `NOT held off`,就要自己去電源設定改。

### 程式擋不掉的三件事,要自己弄

**一、蓋螢幕。** 關蓋是**另一條 Windows 政策**,沒有任何程式能覆寫它。

> 控制台 → 電源選項 → **選擇關閉筆記型電腦上蓋的功能** →
> 「電源已接上」那欄選 **不進行動作**

**二、電池。** 一定要**插著電**。用電池跑,Windows 會降頻,而且多數電源計畫
會照樣進睡眠。

**三、Windows Update 自動重開機。** 這是整夜跑最常見的殺手。

> 設定 → Windows Update → **暫停更新**(先暫停一週)

### 還有兩件實體的事

**散熱。** GPU 滿載八小時的筆電會很燙。放**硬的平面**上(不要床、不要沙發),
出風口不要擋住。過熱降頻會讓 75 步/秒掉到一半。

**斷掉也不會全部白費。** 每 **25,000 步**存一次檔,最多損失那一段。再打同一行
指令就從斷點接下去 —— 續訓會照卡片重建同一架飛機,不會偷偷換設定。

### 背景執行:關掉終端機、登出、重開機都不會中斷

```
scripts/train_background.bat --name v5
```

訓練跑在一個**最小化的視窗**裡,原本那個終端機可以關掉。停止不要按 X:

```
scripts/train_stop.bat --name v5      本次進度會存好再退出
scripts/train_status.bat              看它現在跑到哪
```

`train_stop` 是放一個 `STOP` 檔進 session 資料夾,訓練每一步檢查一次,看到就
存檔退出 —— 跟 Ctrl+C 走同一條路。**直接關視窗會損失最多 25,000 步。**

### 重開機自動接續

```
scripts/train_autoresume.bat          做一次就好
```

註冊一個**登入時觸發**的 Windows 排程工作:下次登入時,它會找出還沒練完的
session 自動接下去。Windows Update 半夜重開機,原本會浪費整晚,現在只浪費到
你早上登入為止。

> 用登入而不是開機觸發:開機觸發要嘛跑在 SYSTEM 帳戶,要嘛存你的密碼,
> 為了省下「凌晨三點重開到早上登入」那幾小時,兩個都不划算。

關掉:`scripts\train_autoresume.bat /remove`

### 花錢之前:先量時間花在哪

```
scripts/profile.bat models/competition/v4
```

**不要在訓練跑的時候跑它** —— 兩個會互相搶機器,量出來的是打架的結果。腳本會
自己擋下來。

實測(訓練中看 `nvidia-smi`):**GPU 使用率 33%、6 GB 顯存只用 429 MB。**
瓶頸不是顯卡算力,也不是顯存 —— 所以「租一張更好的卡」這個直覺**可能是錯的**。

這個工具做兩次計時再相減:模擬本身跑 N 步要多久、同樣 N 步走 `learn` 要多久,
差額就是學習的成本。然後直接告訴你該買什麼:

| 結果 | 意思 | 該做的 |
|---|---|---|
| 學習佔 > 65% | `--gradient-steps -1` 配 8 worker = 大量很小的 GPU 呼叫 | **不要買硬體**,改 `--gradient-steps 2` 或 `--batch-size 512` |
| 模擬佔 > 65% | JSBSim 是 CPU,而且可以平行 | **加 `--workers`**(免費);真要租就租核心多的,不是卡貴的 |
| 各半 | 沒有單一瓶頸 | **什麼都不用買** |

**三種結果裡有兩種不用花錢。**

> 這個檔案原本叫 `profile.py`,十分鐘後改名。`train.py` 是當腳本跑的,所以
> `backend/competition/` 會排在 `sys.path[0]`,而 `cProfile` 第一行就是
> `import profile` —— 它會拿到我們的檔案。torch 會 import cProfile,於是
> **訓練整個起不來**,而錯誤訊息出現在 torch 內部六層深的地方,既沒提到這個檔案
> 也沒提到衝突。現在有一個測試會檢查 `competition/` 底下所有模組名稱,
> 不讓任何一個蓋掉標準函式庫。

### 真的想關電腦的話

只剩租雲端 GPU 一條路。可行,但要花錢、要另外架環境、要把程式和訓練資料搬上去,
是一個獨立的專案。**目前的建議是先不要** —— 一次訓練 7~8 小時,插著電蓋上螢幕
睡一覺就好,把時間花在調實驗上比花在架機器上划算。

## 四之四、量到的:93% 是學習,不用租機器

```
scripts/profile.bat models/competition/v4
```

```
Learning is 93% of the time, the simulation 7%.
```

配上訓練中 `nvidia-smi` 讀到的 **GPU 使用率 33%、6 GB 只用 429 MB**,結論是:

**顯卡是瓶頸所在,但它閒著。** 問題是**呼叫太碎**(`--gradient-steps -1` 配 8 個
worker = 每個向量步做 8 次小更新),不是卡太慢。

| 直覺 | 實際 |
|---|---|
| 租一張更好的卡 | **沒用** —— kernel launch 不會因為卡貴而變快 |
| `--workers` 開大一點 | **沒用** —— 模擬只佔 7%,而且 `-1` 讓更新次數跟著 worker 走 |
| `--batch-size 512` | **這個** —— 呼叫次數不變,每次做更多事,卡正閒著 |
| `--gradient-steps 2` | 可能快三四倍,**但每筆資料的更新量掉到四分之一** —— 那正是先前量過會變差的設定 |

**先動 batch size,不要先動 gradient steps。**

### ⚠️ 先更正一個建議

我前面建議 `--reward score`。**實測之後那是錯的。**

搖桿置中必定墜毀的整回合,四種獎勵的總分:

| 模式 | 總獎勵 | |
|---|---|---|
| `reference` | −10,477 | |
| **`score`** | **+174.6** | ← **墜毀卻拿正分** |
| `margin` | −29.9 | ✅ |
| `shaped` | −71.9 | ✅ |

位置優勢分永遠 ≥ 0,而墜毀只扣一次 −10。2,928 幀的正分把它淹掉了。
**`score` 會教策略「撞地沒關係」。**

### 新的獎勵模式

| 模式 | 是什麼 | 用途 |
|---|---|---|
| `reference` | 主辦方的 | 對照組 |
| `score` | 競賽計分,單邊 | **量測用,不要拿來訓練** |
| **`margin`** | 我方減對方 | 規則比的就是這個差 |
| **`shaped`** | margin + 論文缺的項 | 攻擊錐太窄,需要坡度 |

`shaped` 補的是:朝機首方向的**軟坡度**(1° 硬指標在策略沒進去過之前梯度是零)、
`Γ_B(d)` 距離窗、衝過頭懲罰、接地懲罰。

### 防墜底線 —— 效果最大的一項

```bash
train.bat --ground-avoidance
```

規則明文允許(公告說明 一.1.(2) 把 Rule-Base 和強化學習並列)。

**實測,搖桿置中的策略對上參考對手:**

| | 墜毀率 | 勝率 | 分差 |
|---|---|---|---|
| 無地板 | **100%** | 0% | −19 |
| **有地板** | **0%** | **67%** | **+32** |

每一回合都撐滿五分鐘。**這是一個什麼都不做的策略。**

> 第一版我把升降舵正負號搞反了,結果它**更早**撞地(2766 對 2928 幀)。
> 實測 +0.5 升降舵三秒內把俯仰角帶到 −14.7°,**正號是機首向下**。
> 已修,而且有三個測試會抓這個錯。

#### 第二次修:它只救得了淺俯衝

上面那張表是拿**搖桿置中**的策略量的 —— 一架緩緩下沉的飛機。把同一塊地板裝到
一個真的在機動的策略(run1)上面,墜毀率是 **45%**,不是 0%。

用 48 種進入姿態(4 種高度 × 4 種俯衝角 × 3 種滾轉角)直接量地板本身:

| 地板設定 | 墜毀 | 最高 G | 超過 9G 的代價 |
|---|---|---|---|
| **舊的(0.6、8 秒、8k)** | **28/48** | 22.1 | 333 分 |
| 0.843、8 秒、8k | 5/48 | — | 167 分 |
| 1.0、8 秒、8k | 4/48 | — | 333 分 |
| **現在的(1.0、12 秒、15k)** | **2/48** | 7.9 | 150 分 |

三個獨立的缺陷:

**一、桿量曲線把拉桿吃掉三分之二。** `EXPONENTS[1] = 3.0`,升降舵是三次方曲線。
地板寫 `elevator=0.6`,`0.6³ = 0.216` 才是送到舵面的。追蹤一次 60° 俯衝:
**連續 8.5 秒要 −0.60、拿到 −0.22**,全程最高 3.4 G,對著 9 G 的預算。
`elevator` 是**桿量不是舵量**,現在是 1.0 =「曲線願意給多少就要多少」。

**二、8 秒不夠。** 從一萬呎 60° 俯衝,地板在 6,173 ft 觸發,還剩 8.4 秒。
Mach 0.9 配 0.216 舵量的俯仰率約 4.3°/秒,要改 65° 的俯衝角**需要 15 秒**。

**三、8,000 ft 的天花板擋住了最該觸發的那一刻。** 追蹤裡 t=3.0 秒時飛機在
8,078 ft —— 高於天花板,不准觸發。白白丟掉三秒半。

**代價量過了,不是用猜的。** 拉桿量改大**完全不增加干擾** —— 它不改變什麼時候
介入,只改變介入時拉多用力(三種桿量的觸發幀數都是 4,097,一模一樣)。真正付錢
的是提前觸發:8 秒 → 12 秒,地板拿走的操縱時間從 14.9% 變 20.3%。天花板
8,000 → 15,000 只要 +0.3 個百分點,再往上完全沒差。

> 48 個案例裡只有一個超過 9G,而且那 63.5 G 是在**高度 3 呎**讀到的 ——
> 那是觸地的地面反作用力,不是改出。改出本身最高 7.9 G。

**已經練好的 session 不受影響。** 卡片存的是 `asdict(GroundAvoidance)`,五個欄位
全部寫進去,所以 run1 重載出來的還是舊的 0.6/8 秒/8k。要拿新地板量舊模型,用
`evaluate.bat --ground-avoidance`,報表會標 `+floor`。

#### 續訓拿到的是卡片上那一塊,不是今天的預設值

改預設值馬上暴露一個洞:續訓時 `train.py` 原本是 `GroundAvoidance() if
args.ground_avoidance else None` —— 卡片記的五個欄位被壓成一個 `True`,再用
**現在的**預設值重造。也就是 9/26 之前開的每一個 session,下次續訓都會在中途
無聲地換掉飛機。

現在帶過去的是那個 dict 本身。**續訓 = 同一架飛機,不管預設值後來怎麼變。**

要把新地板裝到舊 session 上,得**明確地講**:

```bash
train.bat --name v2 --ground-avoidance    # 明講 = 今天的預設值
```

明確給的旗標永遠蓋過繼承來的值,然後 `check_compatible` 會攔下來告訴你這是
另一個實驗 —— 那正是它該做的事。

### G 限制器 —— 高速轉彎率加倍

```bash
train.bat --g-limit 9
```

範例客戶端在 Mach 0.8 以上把升降舵砍到 0.4,理由寫的是「9G 罰則」。**它是用速度
去猜 G。** 表 2 給的升降舵是 −1~+1,公告說明 五.3.(2).C 說客戶端可以改寫,所以
兩種限制法都是我們自己選的。

最大轉彎率實測(滿油門、G 壓到極限):

| | 19,000 ft / 500 kt | 3,000 ft / 500 kt | 3,000 ft / 350 kt | 最高 G |
|---|---|---|---|---|
| **Mach 0.4(範例)** | 6.2 deg/s | 8.8 deg/s | 16.4 deg/s | 6.6 |
| **G 限制,餘裕 2** | **12.1** | **15.7** | **16.4** | 7.9 |
| 完全不設限 | 12.1 | 17.1 | 16.4 | **9.3 → 2,917 分** |

**該綁的地方沒綁,不該綁的地方綁死。** 高速時它把轉彎率砍半;真正會超 9G 的
低空高速,它也只擋到一部分;慢速時它根本不存在。

**G 值本來就在 OBS 封包裡**(26 個 double 的 `own_g_acc`),不用猜。所以直接對
G 設限:低於 7G 全權交給策略,7→9 之間線性收,9 以上歸零,而且**只收讓 |G| 變大
的那個方向** —— 正在從高 G 拉出來的時候搶操縱桿是最糟的時機。

轉彎半徑同時從 2,569 m 掉到 1,076 m。**開火窗口是 500–3,000 ft = 152–914 m** ——
用範例的限制,飛機在高速下的轉彎半徑比整個開火窗口還大兩倍半,物理上不可能
邊轉邊留在窗口裡。這大概就是 `killed` 一直是 0% 的一部分原因。

> **符號陷阱,第二次。** 這個模型裡**拉桿產生負 G**(升降舵 −1.0 配
> `n-pilot-z-norm` −9.34)。第一版我把「這個輸入正在加載飛機」寫成兩者**異號**,
> 結果它在 −9.3G 全桿的時候判定「沒在加載」,headroom 已經是 0.00 還是把
> −1.000 原封不動送出去,連續 2.9 秒。同號才對。已修,四個測試會抓。

**預設是關的。** 不給 `--g-limit` 就完全是範例客戶端的行為 —— 9/26 之前練的每一個
模型學的都是那架飛機,不能中途換掉。

## 九、對手:從靶機到對手池

### 為什麼這件事比調參數重要

主辦方的參考對手**從不機動** —— 它的轉彎分支在原始碼裡是被註解掉的。實測五分鐘後
它在 **45 公里外**還在直線飛。

一個**什麼都不做**的策略,只靠防墜地板,就能贏它三分之二的回合。

**對靶機的勝率會在還沒學會打仗之前就飽和。** 而比賽當天的對手是別隊的 agent。

### 三種新對手

| `--opponent` | 行為 | 用途 |
|---|---|---|
| `reference` | 靶機,直線飛 | 對照組,主辦方模型唯一見過的 |
| `level` | 更簡單的直線保持 | — |
| **`pursuit`** | **轉向我方** | 有基本 BFM 的腳本對手 |

實測 `pursuit` 的方位角從 −43° 收斂到 +8°,距離穩在 14 km 而不是拉開到 45 km ——
**它真的在追**。

`--opponent-aggression` 縮放它的垂直追瞄強度,一排不同的值就是一個課程。

> ⚠️ **我沒有證明 `pursuit` 比較難打。** 用會逃跑的退化基準線比不出來 ——
> 兩邊都在 14 km 外,距離係數都是 0.1,分數是噪音。我能驗證的是它做到它宣稱的事。
> 「哪個對手訓練效果好」要靠你的 GPU 跑出來。

### 對手池與 PFSP

```bash
train.bat --name v3 --reward margin --ground-avoidance --action-repeat 6 \
          --gamma 0.995 --gradient-steps -1 \
          --opponent-pool models/competition/pool
```

每一回合從池裡抽一個對手。抽樣規則照 **PHANG-MAN 論文的門檻**:

1. 一開始**均勻**抽
2. 每個對手都打過 **100 場**、而且整體勝率 **> 50%** 之後
3. 改成**依勝負比加權** —— 打不贏的抽中機率高
4. 機率夾在 **0.2% ~ 11.7%**(沒有人會被完全放棄,也沒有人會霸佔)

**Self-play 的做法就是往池子裡丟自己的存檔:**

```bash
# 每練一段就快照一次,快照本身就是階梯
copy models/competition/v3/checkpoint.zip models/competition/pool/v3-2m.zip
```

`--opponent-pool` 吃檔案也吃資料夾。資料夾裡的每個 `.zip` 都是一個對手。

### 一個刻意的取捨

**每個 worker 各自持有一份池和一份 league,獨立抽樣。**

集中式的 league 需要把選擇送到每個子行程、再把結果送回來,而 `SubprocVecEnv`
沒有乾淨的地方放這兩件事。獨立抽樣的代價是統計力 —— 8 個 worker 會各自跑到
100 場門檻,而不是一起跑到 —— 換來的是**完全沒有跨行程協調**的實作。

### 還沒做的

**觀測特徵擴充**(速度差分、能量狀態、對手角速度)。改了就再也載不進主辦方的
模型,而且是最大的單一改動。值得自己一輪,不適合塞在這批裡。

## 十、觀測特徵


### 為什麼

參考的 20 維編碼漏掉了一些**同一個封包裡就有**的東西。最嚴重的一個:

> **策略看不到自己的 G 值。**

> 20 維狀態裡沒有它,也沒有任何能推出它的東西。
> **策略被一個它觀測不到的量處罰。** 那不是難學,是學不了。

補了 10 維,全部從表 1 的 26 個 double 推導,**沒有用到任何額外資訊**:

| 新增 | 為什麼 |
|---|---|
| `own_g_load` | 計分在罰它 |
| `own_calibrated_speed` | 初始條件就是用校正空速定義的,狀態裡只有真空速 |
| `enemy_speed` | 對手速度向量只被拿去算方位角,大小被丟掉 |
| `own_specific_energy` | 高度 + 速度²/2g,纏鬥的核心量 |
| `energy_advantage` | 我方減對方 |
| `azimuth_rate` / `elevation_rate` / `aspect_rate` | 狀態裡只有位置,沒有它們的變化率 —— 策略分不出正在咬上還是正在脫離 |
| `enemy_turn_rate` | 對手速度向量的轉動速率 |
| `round_elapsed` | 早擊殺多 290 分,時間到比分差。策略原本完全不知道剩多久 |

### ⚠️ 代價

**30 維的策略載不進主辦方的模型,他們的也載不進我們的。** 這是能力換相容性,
不是合規問題 —— 所有輸入都來自表 1。

所以它是 `--observation` 選項,不是改動。**`state.py` 一行都沒動**,參考編碼對
主辦方原始函式的差分測試照樣全過。

### 一個記下來的正負號

`n-pilot-z-norm` **拉桿時是負的**。實測:平飛 −0.40、4G 拉桿 −4.24、推桿 +3.75。
機身 Z 軸朝下,所以正 G 在這個欄位是負值。

保留原始約定沒有翻轉,而且順帶驗證了計分用 `abs(g_load) > 9` **是對的** ——
它同時抓 9G 拉桿和 −9G 推桿。

(升降舵的正負號咬過我一次,所以這次先量再寫,而且釘進測試。)

## 為什麼零擊殺:去讀了文獻,然後回頭算自己的獎勵

2026-09-28。v6 在射擊帶待了 55.3 秒、擊殺 0%。在猜下一組參數之前,先去看別人
怎麼解這個問題。

### 文獻怎麼做

**PHANG-MAN**(Pope、Ide 等,DARPA AlphaDogfight Trials,arXiv 2105.00990,
Lockheed Martin,決賽第二名)—— 也就是我們 `ShapedReward` 已經引用的那篇。
重讀之後,關鍵在**它有兩個追蹤項,我們只抄了一個**:

| 項目 | 形狀 | 作用 |
|---|---|---|
| `r_θt = −θ̄t · λ` | 全域線性(λ = 4/9) | 從 90 度收到 20 度的粗調 |
| `r_gunsnap = Γ_B(d) · [1 − S(θ̄t, 1e5, 1/180)]` | **logistic,陡度 1e5,中心 1/180** | 一度錐邊緣的**階梯式**大獎 |

`S(x, α, x₀) = 1/(1+e^(−α(x−x₀)))`。陡度 1e5 幾乎就是在 1 度處的一個階梯。

其他經常出現的形式是 `r_adv = (1 − θ_ATA/π) · exp(−d/D_max)`(多篇階層式空戰
論文),同樣是「角度線性 × 距離指數」的組合。

### 我們的獎勵,實際算出來

`competition/rewards.py` 的追蹤項只有一個,而且是線性的:

```python
aim = max(0.0, 1.0 - geometry.track_angle_deg / 180.0)
```

實際梯度:

| θ | aim | 該段的報酬 |
|---|---|---|
| 90° → 40° | 0.500 → 0.778 | **+0.278** |
| 40° → 1° | 0.778 → 0.994 | +0.217 |
| 5° → 1° | 0.972 → 0.994 | **+0.022** |

**從 90 度收到 40 度,比從 40 度一路收到擊殺還值錢。** 而真正決定得不得分的
最後五度,只佔整個追蹤獎勵的 2.2% —— 幾乎是平的。

這正好解釋 v6:粗幾何(距離、大致朝向)有厚報酬,它學得很好(55.3 秒);
細瞄準幾乎不發錢,它就沒學(0 擊殺)。**不是它不會,是我們沒付錢。**

### 課程順序:我們做反了

PHANG-MAN 的排程寫得很明確:

> 一開始只對「簡單」的腳本對手訓練。勝率超過 50% 之後,才加入「聰明」的對手。

之後從 30 個對手裡依「最近 100 場勝率」加權抽樣,機率夾在 0.2%–11.7% 之間。

我們是直接上 v4+v5 的池。而 v6k(只打內建 drone)擊殺 55%、v6(直接打池)
擊殺 0% —— 資料跟文獻說的完全一致。

### 另外兩條值得記下的線索

1. **回放緩衝區裡沒有錐**。PHANG-MAN 把初始條件偏向武器接戰區(WEZ),好讓
   緩衝區裡真的有那些樣本;還把 shooter 策略的血量調高 10 倍來延長接戰時間。
   SAC 從沒進過的狀態學不到東西。
2. **控制頻率**。PHANG-MAN 低階策略跑 **50 Hz**,只有高階選擇器是 10 Hz。
   我們 `--action-repeat 6` 等於**全部都在 10 Hz**。要把機首壓在 1 度內,
   10 Hz 可能太粗 —— 但這跟 γ=0.995 的 20 秒視野是綁在一起的,要一起算。

### 新量的兩欄會直接分辨是哪一種

`<5deg` 和 `best`(commit e65a8be)量的是機首,不是飛機:

| `best` 讀數 | 意思 | 對應上面哪一條 |
|---|---|---|
| ~1.5° | 幾乎到了,但守不住 3 秒 | 控制頻率 |
| ~5–15° | 收到一半就沒動力了 | **獎勵形狀**(最可能) |
| ~40°+ | 根本沒在瞄 | 課程順序 |

先量,再改。

### 再查一次:主辦方的射擊條件是從 AlphaDogfight 抄來的

同一篇論文(arXiv 2105.00990)裡,WEZ 的定義是:

> the locus of points in between **500-3000 ft** that also lie within a
> spherical cone of **2° aperture**

我們 `AttackEnvelope` 的預設值:

```python
half_angle_deg: float = 1.0      # 2 度全角
min_range_ft:   float = 500.0
max_range_ft:   float = 3000.0
```

**一模一樣。** 500–3000 呎、2 度全角。主辦方把 AlphaDogfight 的 WEZ 直接搬過來,
只多加了「累積 3 秒」這個條件(論文本身沒有 dwell 要求)。

這件事的意義比看起來大:**PHANG-MAN 解的就是我們這一題**,不是「類似的題」。
它的設計可以直接對照,不用打折。

### 三個可以直接抄的做法

| 它做的 | 我們現在 | 差距 |
|---|---|---|
| 低階策略 **50 Hz**,只有高階選擇器 10 Hz | **全部 10 Hz**(`--action-repeat 6`) | **5 倍** |
| 血量調高 **10 倍**,「to further increase the ratio of WEZ to non-WEZ memories stored in the replay buffer」 | 沒有對應處理 | 緩衝區裡幾乎沒有錐內樣本 |
| 兩個專門的近戰策略:Aggressive Shooter / Conservative Shooter | 單一策略要同時學飛行和射擊 | 階層式 vs 單層 |

第一條最直接。論文明說 50 Hz 是為了讓低階策略「execute fine-grained control」——
**細控制**。而 action repeat 的文獻也講得很清楚:它會 degrade precise control,
中間被跳過的幀等於丟掉。

第二條是**任務課程**,不是對手課程:他們發現接戰時間太短、緩衝區裡學不到東西,
就在訓練時把接戰**人為拉長**。我們的對應做法是訓練時放寬 `kill_seconds`
(例如 1.5 秒)或放寬錐角,評分時仍用真實的 3.0 秒 —— `scoring.py` 一行不動,
只有訓練環境拿到不同的 `AttackEnvelope`。

### 但還是先看 `deg/s`

文獻給的是很強的先驗,不是我們這架飛機的量測。`deg/s` 除以 10 就是每個決策之間
視線移動幾度;超過 1 度,就證實 10 Hz 是瓶頸,而且跟論文用 50 Hz 的理由對上。
