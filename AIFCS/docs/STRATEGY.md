## 摘要：最大的三個問題不在策略，在設定

我原本以為要調的是獎勵和對手。實際查下去，**前三名的問題都是超參數層級的，而且主辦方
的範例也有同樣的毛病** —— 這代表多數隊伍很可能一起踩。

| # | 問題 | 現況 | 影響 |
|---|---|---|---|
| 1 | 折扣視野比目標還短 | γ=0.99 → **1.7 秒** | 擊殺要累積 **3 秒** |
| 2 | 多 worker 反而少學 | 8 worker → **每 8 筆資料只更新 1 次** | 名目步數灌水 8 倍 |
| 3 | 決策頻率過高 | 60 Hz → 每回合 **18,000 個決策** | 信用分派極困難 |

## 1. 折扣視野 γ 【量】【碼】【文】 — ⚠️ 我原本的說法要修正

有效視野 = `1/(1−γ)` 個 frame。60 Hz 下 γ=0.99 是 **1.7 秒**，而擊殺要累積 **3 秒**。
這個算術沒錯。

**但我原本說「這是缺陷」，過度了。** 【文】PHANG-MAN 也用 **γ = 0.99**，而且拿了第 2 名。

差別在他們怎麼補：

| | PHANG-MAN | 我們現在 |
|---|---|---|
| 結構 | **階層式**：3 個低階策略 + 1 個選擇器 | 單一扁平策略 |
| 低階頻率 | 50 Hz | 60 Hz |
| **高階頻率** | **10 Hz**（每 5 個低階動作一次） | 無 |
| 獎勵 | 每個低階策略有**專屬的密集獎勵** | 單一獎勵 |

**時間抽象在階層裡，不在折扣裡。** 他們的低階策略各自解一個短視野的問題
（咬住、開火、控制區），所以 γ=0.99 夠用。

**修正後的結論：** γ 值得做 A/B，但不是確定的缺陷。
**更有根據的槓桿是時間抽象** —— 而 10 Hz 正好就是他們高階決策的頻率。

## 1b. 網路寬度 【文】 — 這個我完全沒想到

【文】PHANG-MAN 的表 II：

| 參數 | PHANG-MAN | 主辦方範例 / 我們 |
|---|---|---|
| 隱藏層數 | **1** | 2 |
| 每層神經元 | **12,288**（選擇器 7,168） | **256** |
| 激活函數 | ReLU | Tanh |
| 學習率 | 2.0e-4 | 3e-4（我們）/ 2e-4（主辦方） |
| batch | 256 | 256 |
| soft τ | 1.0e-3 | 5e-3（SB3 預設） |
| 熵目標 | −4 | auto |
| replay buffer | 5.0e6 | 1e6 |

論文明講理由：

> Wide and shallow MLP networks such as these have been shown to perform better
> than narrower and deeper MLP networks containing the same number of neurons

**我們是 2×256 = 512 個神經元，他們是 1×12,288 —— 差 24 倍。**
主辦方的範例也是 2×256，所以照抄範例的隊伍會一起卡在這裡。

⚠️ 12,288 對筆電 GPU 太大。但從 512 往上試（2048、4096、單層）是**便宜的 A/B**，
而且不改環境。

## 2. 梯度更新比 【量】【碼】

SB3 的 `train_freq=1` 計算的是 **vec-env 迭代次數**，不是 transition 數。
8 個 worker 下，一次迭代收 8 筆資料，而 `gradient_steps=1` 只做 **1 次**更新。

實測（4 workers、CPU）：

| 設定 | 每筆資料的更新次數 | 速度 |
|---|---|---|
| `gradient_steps=1`（現況） | **0.23** | 352 steps/s |
| `gradient_steps=-1` | **0.90** | 103 steps/s |

**`--workers 8` 不是把學習加速 8 倍 —— 是把每個名目步數的學習量除以 8。**
run1 的 192 萬「步」其實只做了約 24 萬次梯度更新。

⚠️ **這個量測是 CPU 的**，梯度和環境搶同幾顆核心。你的 4050 上梯度跑 GPU、
環境跑 CPU，代價應該低很多 —— **但我沒辦法在這裡量到那個數字**。

【碼】主辦方範例同樣沒設 `gradient_steps`，而且 `learning_starts=1000000`
（前一百萬步純亂飛）。

## 3. 決策頻率與 action repeat 【文】【推】

【文】文獻稱這個為 *granularity trap*：決策間隔越細，一個任務需要的決策數越多，
信用分派越難。Action repeat（把同一個指令保持 d 個 frame）把有效視野從
`1/(1−γ)` 變成 `1/(1−γ^d)`，TD 學習得到等比例的加速；同時讓隨機探索更容易碰到
**高階機動**，因為一連串低階動作要湊成一個機動的機率隨長度指數下降。

我們的情況特別適合，有一個額外理由：**搖桿變化率上限本來就是 0.026/frame**。
升降舵從中立到滿舵要 38 個 frame。**政策每 1 frame 改變心意，但舵面 38 frame 才動得完**
—— 60 Hz 的決策頻寬有絕大部分是浪費的。

| | 現況 | 建議 |
|---|---|---|
| 決策頻率 | 60 Hz | **10 Hz**（repeat 6） |
| 每回合決策數 | 18,000 | **3,000** |
| γ | 0.99 | **0.995** |
| 有效視野 | 1.7 秒 | **20 秒** |

⚠️ 規則要求**每個 frame 都要回一個封包**。Action repeat 是「送同一個指令」，
不是「不送」。完全合規。

⚠️ 這改變了 plant，所以**訓練和比賽兩邊都要改**，而且是新的 session。

## 4. 獎勵 【量】【文】 — 主辦方的獎勵是這篇論文的**刪節版**

比對之下發現的：

| 項 | PHANG-MAN | 主辦方範例 |
|---|---|---|
| 接地懲罰 | `−4·[1−S(h, 1/20, 1300)]` | `−5·(1−S(h, 1/20, 1300))` |
| 接近率 | `(vc/500)·[…]·S(d, 1/500, 2900)` | `clip(Δd·0.5,−2,2)·S(d, 1/500, 2900)` |

**`1/20`、`1300`、`1/500`、`2900` 四個常數一字不差。** 主辦方的參考獎勵就是從這篇
來的，然後**砍掉了一半**。

砍掉了什麼：

| 缺的項 | 公式 | 為什麼重要 |
|---|---|---|
| `r_rel.pos.` | `(θ̄t−2)·S(φ̄a,18,½) − θ̄t + 1` | **同時看追蹤角和方位角**，還會罰「讓對手取得同樣位置」 |
| `r_gunsnap(blue)` | `Γ_B(d)·[1−S(θ̄t,1e5,1/180)]` | **`Γ_B(d)` 就是距離窗** —— 主辦方缺的正是這個 |
| `r_gunsnap(red)` | `−Γ_R(d)·S(φ̄a,800,178/180)` | **被咬的懲罰** |
| `r_tooclose` | `−2·[1−S(φ̄a,18,½)]·S(d,1/50,800)` | 罰衝過頭 |
| `r_φa` | `−φ̄a` | 方位角單獨成項 |

`Γ_B(d)` 是一個以約 1,950 呎為中心的窗（1,000 呎升起、2,900 呎落下）——
**主辦方的攻擊包絡是 500–3000 呎，這個窗形狀正好對得上。**

### 我們的 `ScoreReward` 還缺一件更關鍵的事

已量過：參考獎勵對距離完全平坦（200 m 和 6 km 都給 2.00），競賽計分差 29 倍。
所以 `--reward score` 仍然是對的。

**但 `ScoreReward` 只獎勵我方優勢，完全沒有防守項。**

而規則寫的是「**作戰優勢分高者勝利**」—— 那是一個**比較**。
讓對手拿不到分，和自己拿分，在判定上等價。

```
現在：   reward = 我方每幀優勢
應該：   reward = 我方每幀優勢 − 對方每幀優勢
```

右邊那個**就是決定回合勝負的量**。`CompetitionRound` 已經同時算了雙方的
`SideScore`，所以這是幾行的改動。**這是從規則推出來的，不是抄論文。**

## 5. 對手：PFSP 【文】 — 論文給了具體參數

【文】PHANG-MAN 的做法，照抄他們的門檻：

1. 先只對**腳本化的「簡單」對手**訓練
2. 勝率 > **50%** 後，加入「聰明」對手：自己的舊版本、單獨的低階策略、
   模仿其他隊伍風格的 agent
3. 每個對手都打過 **100 場**、整體勝率 > 50% 後，
   改成**依最近 100 場的勝負比加權抽樣**，每場之後動態更新
4. 抽中機率**下限 0.2%、上限 11.7%**（避免把時間浪費在太弱或太強的對手上）
5. 總共 **30 個不同對手** + self-play

現況：我們只有 `reference` 和 `level` 兩個固定對手。

⚠️ **SAC 和 self-play 合不來** —— replay buffer 裡裝著對上舊對手的資料。
但注意 PHANG-MAN **確實用 SAC** 配 PFSP，靠的是 5e6 的大 buffer 和優先經驗回放
（PER）。所以「一定要換 PPO」是我推論過頭了，**這一項要實驗。**

## 6. 觀測特徵 【碼】

**這也是我們的。** HOST 送 26 個 double；那 20 維狀態是**參考程式對它們的編碼**，
不是規則。目前我們照抄它，理由是「讓主辦方的策略能原封不動載進來」——
一旦我們不再需要載入他們的策略，這個理由就消失了。

可以加的（全部是 26 個 double 的函數，不需要額外資訊）：

- **對手的角速度/加速度**（從連續兩幀的速度差分）—— 目前完全沒有
- **接近率的時間導數**
- **我方能量狀態**（比能量 = 高度 + v²/2g），BFM 的核心量
- **對手的能量狀態**，以及能量差
- **歷史**：frame stacking 或 LSTM —— 目前策略看不到任何過去

⚠️ 改觀測 = 改環境 = 新 session，而且不能再載入主辦方的模型。

## 8. 比賽當天的一個陷阱 【文】

【文】PHANG-MAN 遇到的，值得記下來：

> 在**不同 GPU 架構**上部署時，相同的情境會產生明顯不同的結果 —— 相同的輸入、
> 相同的網路、相同的 docker container，輸出差約 **1e-6**，
> 而這個差距**足以把一場勝利變成失敗**。

他們的對策是**截斷狀態與動作的數值**。

我們的情況：訓練和比賽都在同一台筆電，所以風險低。
但**如果你打算換機器比賽，就會踩到。**

## 現實檢查 【文】

> low-level policies took up to **a month** to achieve maximum performance

那是在 Ape-X 式的**分散式**訓練框架上，多個 actor + 中央 learner + 優先經驗回放。

**我們有 42 天和一台筆電 GPU。**

所以不要期待做到 PHANG-MAN 的規模。策略應該是：**挑那些「便宜且多數隊伍不會做」的**。
主辦方的範例有三個明顯的弱點（獎勵刪節、網路窄、gradient_steps），
照抄範例的隊伍會一起卡住。
