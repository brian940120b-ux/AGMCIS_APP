# 升級計畫 — 以贏得比賽為目標

2026-09-26。距離比賽 **42 天**。

前提：`TUNING.md` 已界定規則允許改什麼。這份講**改什麼最有用、為什麼、怎麼驗證**。

每一項標證據等級：
**【量】** 我在這台機器上實測過 ·
**【碼】** 讀主辦方或函式庫原始碼確認 ·
**【文】** 查到的公開研究 ·
**【推】** 我的推論，還沒驗證

## 摘要：最大的三個問題不在策略，在設定

我原本以為要調的是獎勵和對手。實際查下去，**前三名的問題都是超參數層級的，而且主辦方
的範例也有同樣的毛病** —— 這代表多數隊伍很可能一起踩。

| # | 問題 | 現況 | 影響 |
|---|---|---|---|
| 1 | 折扣視野比目標還短 | γ=0.99 → **1.7 秒** | 擊殺要累積 **3 秒** |
| 2 | 多 worker 反而少學 | 8 worker → **每 8 筆資料只更新 1 次** | 名目步數灌水 8 倍 |
| 3 | 決策頻率過高 | 60 Hz → 每回合 **18,000 個決策** | 信用分派極困難 |

## 1. 折扣視野 γ 【量】【碼】

有效視野 = `1/(1−γ)` 個 frame。60 Hz 下：

| γ | 視野 |
|---|---|
| **0.99（現況）** | **1.7 秒** |
| 0.995 | 3.3 秒 |
| 0.999 | 16.7 秒 |
| 0.9995 | 33.3 秒 |

**擊殺條件是累積 3 秒的追蹤。回合是 300 秒。**
價值函數看得到的未來，比它要達成的目標還短。

一個只看得到 1.7 秒的價值函數，無法評價「現在往左轉、六秒後咬到對方尾巴」——
那個報酬在它的地平線之外。

【碼】主辦方 `train.py` 也是 `gamma=0.99`，他們那顆 3.14 億步的模型同樣受限。

## 2. 梯度更新比 【量】【碼】

SB3 的 `train_freq=1` 計算的是 **vec-env 迭代次數**，不是 transition 數。
8 個 worker 下，一次迭代收 8 筆資料，而 `gradient_steps=1` 只做 **1 次**更新。

實測（4 workers、CPU）：

| 設定 | 每筆資料的更新次數 | 速度 |
|---|---|---|
| `gradient_steps=1`（現況） | **0.23** | 352 steps/s |
| `gradient_steps=-1` | **0.90** | 103 steps/s |

**`--workers 8` 不是把學習加速 8 倍 —— 是把每個名目步數的學習量除以 8。**
run1 的 192 萬「步」其實只做了約 24 萬次梯度更新。

⚠️ **這個量測是 CPU 的**，梯度和環境搶同幾顆核心。你的 4050 上梯度跑 GPU、
環境跑 CPU，代價應該低很多 —— **但我沒辦法在這裡量到那個數字**。

【碼】主辦方範例同樣沒設 `gradient_steps`，而且 `learning_starts=1000000`
（前一百萬步純亂飛）。

## 3. 決策頻率與 action repeat 【文】【推】

【文】文獻稱這個為 *granularity trap*：決策間隔越細，一個任務需要的決策數越多，
信用分派越難。Action repeat（把同一個指令保持 d 個 frame）把有效視野從
`1/(1−γ)` 變成 `1/(1−γ^d)`，TD 學習得到等比例的加速；同時讓隨機探索更容易碰到
**高階機動**，因為一連串低階動作要湊成一個機動的機率隨長度指數下降。

我們的情況特別適合，有一個額外理由：**搖桿變化率上限本來就是 0.026/frame**。
升降舵從中立到滿舵要 38 個 frame。**政策每 1 frame 改變心意，但舵面 38 frame 才動得完**
—— 60 Hz 的決策頻寬有絕大部分是浪費的。

| | 現況 | 建議 |
|---|---|---|
| 決策頻率 | 60 Hz | **10 Hz**（repeat 6） |
| 每回合決策數 | 18,000 | **3,000** |
| γ | 0.99 | **0.995** |
| 有效視野 | 1.7 秒 | **20 秒** |

⚠️ 規則要求**每個 frame 都要回一個封包**。Action repeat 是「送同一個指令」，
不是「不送」。完全合規。

⚠️ 這改變了 plant，所以**訓練和比賽兩邊都要改**，而且是新的 session。

## 4. 獎勵 【量】

已量過（機首正對、距離不變）：

| 距離 | reference 每幀 | competition 每秒 |
|---|---|---|
| 200 m | 2.00 | 3,440 |
| 6000 m | **2.00** | **120** |

參考獎勵對距離完全平坦。**用 `--reward score`。**

## 5. 對手：PFSP 【文】

【文】純 self-play 會過擬合到單一對手並遺忘舊策略。Fictitious Self-Play 讓
agent 對過去策略的經驗分布學最佳反應；**Prioritized FSP (PFSP)** 再依勝率加權
抽樣，優先對上難纏的版本，避免把時間浪費在太弱或太強的對手上。

現況：我們只有 `reference`（照抄主辦方的目標機）和 `level` 兩個固定對手。
**對固定對手練出來的策略，遇到會反擊的對手會很脆。**

分階段：
1. 固定對手（現在）→ 先學會活著和咬尾
2. 加入自己的歷史 checkpoint 池，隨機抽
3. 依勝率加權（PFSP）

⚠️ **SAC 和 self-play 合不來**：replay buffer 裡裝著對上舊對手的資料，對手一換就過時。
league 訓練的標準選擇是 **PPO**（on-policy，沒有這個問題）。
這是一個真正的架構分岔，要用實驗決定，不是用讀的。

## 6. 觀測特徵 【碼】

**這也是我們的。** HOST 送 26 個 double；那 20 維狀態是**參考程式對它們的編碼**，
不是規則。目前我們照抄它，理由是「讓主辦方的策略能原封不動載進來」——
一旦我們不再需要載入他們的策略，這個理由就消失了。

可以加的（全部是 26 個 double 的函數，不需要額外資訊）：

- **對手的角速度/加速度**（從連續兩幀的速度差分）—— 目前完全沒有
- **接近率的時間導數**
- **我方能量狀態**（比能量 = 高度 + v²/2g），BFM 的核心量
- **對手的能量狀態**，以及能量差
- **歷史**：frame stacking 或 LSTM —— 目前策略看不到任何過去

⚠️ 改觀測 = 改環境 = 新 session，而且不能再載入主辦方的模型。

## 7. 防墜底線（混合式）【量】

【量】搖桿置中 49 秒撞地。【文/規則】混合式明文允許
（「Rule-Base、行為樹、…、強化學習」並列）。

一層規則式的保護：低於某高度且下降率過大時，強制接管拉起。
**不改訓練，直接裝在輸出端**，可以單獨驗證。

## 排程（42 天）

| 週 | 做什麼 | 為什麼這個順序 |
|---|---|---|
| **1** | γ + gradient_steps 新 session；run1 當對照組 | 最便宜、影響最大，不動環境 |
| **1** | 防墜底線 | 獨立，不卡訓練 |
| **2** | action repeat（訓練 + 比賽端一起） | 改 plant，要完整的對等測試 |
| **2–3** | `--reward score` A/B | 要前面的設定先定下來 |
| **3–4** | 觀測特徵擴充 | 最大的改動，要有前面的基準線 |
| **4–5** | 對手池 / PFSP，決定 SAC vs PPO | 最貴，但也是最後的天花板 |
| **5** | 方向舵 ±1 的 A/B | 錦上添花 |
| **6** | 凍結、對真實 HOST 驗證、準備第二顆模型 | 注意事項 3 允許回合間換 |

**每一步都用 `evaluate.py` 配對比較（相同 seed），輸給對照組就退回。**
